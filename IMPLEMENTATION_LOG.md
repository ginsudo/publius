# IMPLEMENTATION_LOG.md — Publius

This is a stable reference for what has actually been built in the Publius repository, written for someone joining a fresh advisory thread. It complements `CLAUDE.md` (standing decisions, "what to do"), `DECISIONS.md` (architectural decisions with reasoning, "why we decided this"), and `data/SCHEMA.md` (the cross-corpus data schema). Those documents tell you what the project should be. This document tells you what currently exists and what does not.

## Phases complete

### Phase 0 — Corpus acquisition and parsing (Federalist + Tocqueville)

The two acquired corpora are parsed into the cross-corpus base schema and live as static JSON in `data/`.

**Federalist Papers** — 85 papers, 71 footnotes, 0 open issues. Source: a Project Gutenberg edition. Parser at `data/federalist/parse.ts` produces `data/federalist/federalist.json`. Authorship attribution preserves the disputed-twelve set (papers 49–58, 62, 63) with explicit `authorship_status` values rather than collapsing to a single attribution. A `SOURCE_FIXUPS` layer in the parser holds raw-text corrections so the upstream source remains traceable.

**Tocqueville (Democracy in America)** — 124 items, 340 inline footnotes, 0 open issues. Source: Project Gutenberg's French original. Parser at `data/tocqueville/parse.ts` produces `data/tocqueville/tocqueville.json`. Items include chapters, avertissements, introductions, an appendix, and end-notes across both volumes. Every Tocqueville item carries a `translation` field initialized to `null`; this is the editorial gate documented below.

**SCOTUS opinions** — not yet acquired. The third corpus is the project owner's curated-list decision and has not been started.

**Path from v0.1 to v0.2 (today's work):**

v0.1 was tested, closely examined, and rewritten as v0.2 over the course of a single working session. The path is captured here in narrative form because cross-session continuity benefits from knowing the experiments and reasoning behind the lock decision, not just the decision. The DECISIONS.md entry for v0.2 (commit `464142e`) is the architectural decision; this is the trace that produced it.

*Five-clause ablation against the v0.1 closing section.* Each of the five sentences in the closing "what you are not" section was removed in turn — `system-prompt-v0.1-no-clause1.md` through `system-prompt-v0.1-no-clause5.md`, generated by a single-occurrence-asserted script and inspected via inline diff before any run kicked off. Each variant was run against three diagnostic questions chosen for the rule each sentence was trying to enforce; results in `prompts/eval/results-v0.1-no-clause{1..5}.md` and the matching baseline at `prompts/eval/results-v0.1-baseline-fresh.md`. No individual sentence was load-bearing: removing any single sentence produced no detectable discipline failure on the diagnostic questions. This ruled out a surgical-rewrite path — there was no single sentence to keep and no single sentence to drop. The closing section either earned its place as a whole or did not. The result is consistent with the holistic-effect view of how prompt language works: prompt sections have effects that do not localize cleanly to individual sentences, and a section either does its work as an integrated unit or it doesn't.

*Run A/B across the full 15-question test set.* `prompts/eval/results-v0.1-runA.md` ran the full v0.1 prompt against all 15 questions; `prompts/eval/results-v0.1-runB.md` ran v0.1 with the closing section removed against the same 15 questions. Three findings emerged. First, the closing section was mostly redundant: the body's discipline rules — attribution, surface-disagreement, no-flattening, mark-out-of-corpus, do-not-editorialize — held without it across all 15 questions in runB, and no discipline failure appeared in runB that did not also appear in runA. Second, the closing section was uniquely doing one thing: enforcing symmetric availability of arguments to multiple interpretive schools on Q7-style questions. RunA on Q7 produced an answer with an explicit symmetry-marking summary table; runB on the same question allowed itself to read the textual evidence as cutting toward fixed-meaning interpretation. Both answers were disciplined; they differed in posture, and the closing section was the source of the symmetry posture. Third, the closing section appeared to suppress analytic depth on Q5, Q14, and Q15: runB produced sharper analytic structure (counter-arguments-each-side-must-answer on Q5, three-fold differentiations on Q14 and Q15, willingness to commit to readings the text supports). The hypothesis: the "you do not decide who is right" framing was reading more broadly than its content, pushing the model toward restraint that suppressed legitimate interpretive moves, not just illegitimate ones. Together with the ablation result, this motivated a structural rewrite.

*Trace-analysis sketch (separate from v0.2).* One line in the v0.1 closing section — "the corpus does not have opinions either; it has arguments, observations, and holdings" — had been guarding against a real type-error: treating the per-turn answer as the locus of position-formation. But the per-turn answer is not the locus of position-formation across an inquiry; the conversation is. This is a per-turn-vs-trace-level distinction. The per-turn prompt's job is to *surface* arguments, observations, and holdings from the corpus with attribution and mode discipline. What an inquiry has *constituted* out of the corpus — the structural argument(s) the user's path has assembled across many turns — is a trace-level property and belongs to a separate artifact. A design sketch of that artifact lives at `notes/trace-analysis-sketch.md` (commit `464142e`); the placement is probably Phase 1.6 or deferred to Phase 5, exact slot is a project-plan decision. v0.2 dropping the corpus-doesn't-have-opinions language is consistent with the distinction: at the per-turn level, the model is reasoning from passages, not constituting positions, and the type-error the guardrail was preventing does not arise. The trace-level is where position-formation actually happens, and the trace-analysis artifact is where the corresponding discipline belongs.

*The v0.2 rewrite.* `prompts/system-prompt-v0.2.md` (commit `f5b39a6`) drops the closing "what you are not" section entirely (runA/B redundancy finding), restructures the rules into the actual flow of work (corpora → handling → answer shape), and makes four targeted additions tied to specific findings:

- A permission-and-prohibition pair: *"You may commit to readings the corpus actually supports… The discipline is not to refuse interpretation; it is to refuse interpretive partisanship."* The negative-plus-positive construction is motivated by both the Q7 finding (the closing section's symmetric-availability work was over-broad) and the Q5/Q14/Q15 depth-suppression finding (the model needs explicit license to commit where the text supports commitment).
- An explicit no-synthesizing-close instruction: *"Do not write closing paragraphs that synthesize positions the corpus has held distinct."* This names the Q14 failure mode that v0.1 had been trying to prevent indirectly through the closing section.
- A light length nudge: *"Length should track the question's complexity; a thirty-word question rarely needs a thousand-word answer."* This partially resolves v0.1's open question A2 (whether a length guardrail is needed); the evidence from runA/B was that lengths tracked complexity reasonably well, but the long-answer-to-short-question failure mode warranted an explicit guardrail.
- A reframing of the verdict-pressing instruction. v0.1's "you do not decide who is right" — an identity-claim about the model — is dropped in favor of *"When the question presses for a verdict the corpus cannot settle… name that the corpus does not settle it, and name what the corpus does permit."* This is a behavioral instruction tied to question shape, not an identity claim about the model. It is also more compatible with the trace-analysis distinction above: identity-language about what the model is or has no place to settle has costs that behavioral instructions do not.

The full v0.2 entry, including what did not change from v0.1, is in `DECISIONS.md` (commit `464142e`).

*Run C against seven diagnostic questions.* `prompts/eval/results-v0.2-runC.md` (commit `f5b39a6`) ran v0.2 against Q5, Q7, Q9, Q10, Q11, Q12, and Q14 — chosen to exercise the v0.2 changes (the depth-permitting questions, the symmetric-availability question, the synthesizing-close failure mode, in-corpus and out-of-corpus shapes). All seven calls returned `end_turn`. Discipline was preserved across all seven; depth was permitted where the textual evidence supports it; no new failure modes appeared. Output lengths were uniformly shorter than runB on the same questions (48–82% of runB length), consistent with the length nudge earning its keep without truncation. This is what produced the lock decision.

*Watch items going forward.* Two flags worth carrying into the next slice. First, outside-corpus factual claims need independent verification when load-bearing for an answer — runC's characterization of *Loper Bright* and the specific number of people Madison enslaved are cases where the discipline of marking "outside the corpus" is met but the underlying factual claim is not itself audited. Mode discipline is not factual discipline. Second, the seven-question diagnostic set is small; runD on the full 15 questions is available as a future cross-check if stronger evidence is wanted later before further changes.

**Phase 1.2 HTTP boundary scaffolded (today's work — 2026-04-27):**

Following the spike, scaffolded the real `app/` directory and exposed the v0.2 system prompt as an HTTP boundary. *What was created.* `package.json` (Next 16.2.4, React 19.2.4, `@types/node ^22`); `tsconfig.json` with `allowImportingTsExtensions: true`, `moduleResolution: bundler`, `strict: true`, `noEmit: true` — JSONC top-comment points back at DECISIONS.md so the next reader knows why those flags are there; `next.config.ts` with `turbopack.root: __dirname` to silence a spurious workspace-root warning caused by a stray lockfile in `$HOME`; `app/layout.tsx` (minimal root layout, title `Publius`); `app/page.tsx` returns `notFound()` (no public landing copy until Phase 1.4 ships UI); `app/api/ask/route.ts` and `app/api/retrieve/route.ts`. The spike's symlink workaround is not present — the real routes live inside the repo root, no symlinks needed. `loadEnv()` is not called from either route; Next's automatic `.env.local` loading suffices, and dropping the explicit call keeps the route clean for Phase 1.4 Vercel deploy where env vars come from the platform.

*Citation type added to `data/eval/query.ts`.* `Citation` is defined as a named type next to `Hit`, not inline as `Omit<Hit, 'text' | 'score' | 'distance' | 'rank' | 'id'>`. The named type gives a single audit point if the projection ever changes, and the route imports `toCitation` from the same module so the projection lives next to the source-of-truth `Hit` type. Citation strips `text` (raw chunk text), `score`/`distance` (similarity numbers), and `rank`/`id` (internal indexing); preserves all corpus and provenance metadata (corpus, kind, item_id, paragraph_index, marker, paper_number, title, authors, authorship_status, date).

*`/api/ask` shape.* POST `{question: string, k?: number}` → `{answer: string, citations: Citation[], usage: {inputTokens, outputTokens, stopReason}, promptSha256: string}`. The system prompt is loaded once at module init via `extractPrompt()` (the same function the harness uses), and the sha256 is computed once at module init. Errors are mapped explicitly: 401 (`unauthorized`), 429 (`rate_limit`), 529 (`overload`), 502 (`upstream_error` for other Anthropic failures), 500 (missing key — `missing_anthropic_key`, `missing_voyage_key`, `unexpected_error`), 400 (`malformed_input` for bad body, empty question, or k out of [1, 25]). Body shape on errors is `{error: string, code: string}`. Nothing silently swallows an error.

*`/api/retrieve` shape.* POST `{question: string, k?: number}` → `{hits: Hit[]}`. Same input validation. No model call, no system prompt, no token usage. Lives at the same boundary because the development inspection surface should not piggyback on the public answer surface — the latter must remain the only path the UI ever depends on. Phase 1.4 will commercialize on `/api/ask`'s shape; `/api/retrieve` exists for diagnostics and may be IP-allowlisted or removed before public deploy.

*Build and type-check.* `next build` clean — Turbopack compile ~650ms, TypeScript type-check ~720ms, two routes registered as dynamic (`ƒ /api/ask`, `ƒ /api/retrieve`), root path static and 404. No errors, no warnings after the `turbopack.root` fix.

### Phase 1.3 — Observability wiring (Langfuse via OTel)

Phase 1.3 wires observability against Langfuse Cloud through OpenTelemetry. The Helicone-vs-Langfuse choice from the early "Observability: wired from day one" decision is resolved in favour of Langfuse — open-source / self-hostable footprint, OTel-native integration, no LLM-traffic proxy. The full architectural entry is `DECISIONS.md` ("Phase 1.3 observability — Langfuse via OTel").

**Locked artifacts (today's work — 2026-04-27):**
- `lib/observability.ts` — single audit point for what gets logged per `/api/ask` call (and per harness run when `LANGFUSE_TRACING=1`). Holds `initObservability()` (SDK boot, shared between Next.js and the harness), `withAskTrace` / `withRetrievalSpan` / `withGenerationSpan` (the three observation helpers), and `classifyError()` (single source of truth for `error.code`/`error.status` shared between the route's HTTP error mapper and the trace's failure attributes).
- `instrumentation.ts` — Next.js instrumentation hook. Calls `initObservability()` when the Node runtime starts; Edge runtime is skipped (sqlite-vec + node:sqlite are Node-only anyway).
- `app/api/ask/route.ts` — wrapped in `withAskTrace` (parent observation, holds question / k / `prompt_sha256` / source / answer) → `withRetrievalSpan` (child, captures top-K ids + scores + two hit-set hashes + latency) → `withGenerationSpan` (Langfuse `generation` observation type so the UI surfaces tokens + model in the generation panel).
- `prompts/eval/run.ts` — same wrapping as the route, but env-gated by `LANGFUSE_TRACING=1` so harness runs do not pollute the trace stream by default. `source: "harness"` distinguishes harness traces from route traces in the UI.
- `scripts/proveit-langfuse.ts` — discardable prove-it script confirming a generic Langfuse span captures a Voyage embed call. Cashed the "no Voyage example in current docs" flag from the Phase 1.3 plan; kept in the repo as a minimal smoke-test entry point for future runtime questions.
- `data/eval/lib.ts` — `loadEnv()` strips matching surrounding single/double quotes from `.env.local` values (dotenv convention). Surfaced when `LANGFUSE_BASE_URL="https://us.cloud.langfuse.com"` was being passed through to the OTel exporter with literal quotes embedded in the URL string.
- New deps in `package.json`: `@langfuse/otel`, `@langfuse/tracing`, `@opentelemetry/sdk-node`. Transitively pulls `@opentelemetry/api`, `@opentelemetry/core`, and `@langfuse/core`.

**Failure-mode discipline.** A Langfuse outage, bad keys, or any SDK error must not affect `/api/ask` behaviour. Three layers of defence: SDK init is wrapped in try/catch and returns `null` on failure (tracing disabled, route runs uninstrumented). The `with*Span` helpers wrap `startActiveObservation` in try/catch with a `started` flag and fall through to running `fn` directly when the wrapper itself fails before `fn` executes. Individual `span.update()` calls swallow per-attribute failures so a single bad attribute does not kill the trace. Verified end-to-end via the test sequence below — bogus keys produce HTTP 200 from `/api/ask` with no error propagated; bad URL produces HTTP 200 with `[observability] exporter error:` logged but request flow unaffected.

**Path from prove-it to landed slice:**

*Prove-it.* The Phase 1.3 plan flagged "no Voyage example in current docs" as a runtime unknown — it was not obvious whether wrapping a Voyage embed call inside a generic Langfuse `startActiveObservation` would produce the expected trace shape. `scripts/proveit-langfuse.ts` resolved this in one minimal script: bare SDK boot, single `startActiveObservation('publius-proveit-voyage', ...)` containing one `voyageEmbed()` call, explicit `sdk.shutdown()`. Trace appeared in Langfuse Cloud with input/output attributes intact. The integration is straightforward; the production helpers in `lib/observability.ts` build on this pattern with the failure-mode discipline added.

*Route + harness wiring.* `withAskTrace` / `withRetrievalSpan` / `withGenerationSpan` were extracted into `lib/observability.ts` rather than scattered across the route and the harness. The single audit point matters: any change to "what we log" (which attributes, hash-ordered vs hash-set, generation model, latency) lands in one diff, not two. The route imports the helpers directly; the harness imports them with an env gate (`LANGFUSE_TRACING=1`) so harness runs that don't need traces don't pay the cost or pollute the trace stream. `source: "route" | "harness"` is a top-level metadata attribute on the parent observation — the Langfuse UI's filter-by-metadata makes route traffic vs harness runs cleanly separable.

*Hit-set hashes.* `withRetrievalSpan` records two SHA-256 hashes over the top-K ids: `retrieval.top10.hash_ordered` (ranking-order, '|'-joined) and `retrieval.top10.hash_set` (alphabetically-sorted, '|'-joined). The two together give a ranking-invariant fingerprint and a ranking-sensitive fingerprint; the cross-session voyage-embedding non-determinism documented in `DECISIONS.md` ("Voyage embeddings are not bit-stable across API calls") makes both worth having. `hash_set` lets a future regression check ask "is this the same hit set?" without false-positives from rank shuffles between runs; `hash_ordered` exposes the rank shuffles when they matter.

*Bogus-key test (initial).* The Phase 1.3 plan called for a bogus-key test: with deliberately bad Langfuse keys, confirm `/api/ask` returns 200 (failure isolated), no trace appears (failure complete), and the SDK error is logged not propagated. Initial run with bogus public+secret keys: HTTP 200 returned from `/api/ask`, no trace appeared in the UI, and no errors in server logs. The first three observable conditions matched the plan; the fourth — "logged not propagated" — was satisfied for "not propagated" but produced silence rather than a `console.error`.

*Silent-failure investigation.* The owner flagged the silent-failure observation as a real spec deviation, not an ops note: the Phase 1.3 plan said "flush/network errors swallowed and console.error'd." Investigation traced the silence to two missing OTel hooks. The OTLP fetch transport calls `diag.warn` / `diag.error` directly for HTTP / network failures, but the default `diag` logger is a no-op. The BatchSpanProcessor's export-result path goes through `globalErrorHandler` from `@opentelemetry/core`, which defaults to a `loggingErrorHandler` that calls `diag.error` — so even that path is silenced when `diag` is no-op'd. Both hooks needed installing.

*Hook installation and validation.* `initObservability()` now sets `diag.setLogger` at `DiagLogLevel.WARN` (mapping `warn`/`error` to `console.error` with an `[observability]` prefix) and registers a `setGlobalErrorHandler` that does the same. With both hooks in place, re-ran the bogus-key scenario — still silent. Lowered `diag` to `DiagLogLevel.ALL` to surface the underlying transport behaviour, which revealed `[obs:verbose] Export succeeded after 0 retry attempts.` Root cause: Langfuse Cloud's OTLP endpoint accepts unknown public keys with HTTP 2xx and filters server-side, so a bad public key produces no transport error to log. The hooks were correctly installed; there was simply no failure for them to surface.

*DNS-failure validation.* To confirm the hooks fire on actual transport failures, set `LANGFUSE_BASE_URL=https://nonexistent-publius-test.invalid` and re-ran the harness with `LANGFUSE_TRACING=1`. Output included `[observability] exporter error: Error: getaddrinfo ENOTFOUND nonexistent-publius-test.invalid` from the global error handler and `[observability] sdk.shutdown failed: ...` from the existing shutdown catch. Repeated the same scenario under the Next.js dev server hitting `/api/ask`; same `[observability] exporter error:` lines surfaced after the BatchSpanProcessor's batch flush. Both contexts produced the expected error logs without affecting request flow. Reverted `diag` log level to `WARN`.

*The bad-credentials silence as a known limitation.* The owner confirmed reading the spec literally — "network errors" means DNS / connection refused / HTTP 4xx/5xx from a real endpoint, all of which now fire the hook. The bad-credentials silence is a Langfuse architecture choice (server-side key filter behind an HTTP 2xx endpoint), not something OTel can detect through the per-request hook. Captured this in `DECISIONS.md` as a known limitation with operational guidance: "if traces stop appearing without console errors, suspect credential rotation first." A future startup-time auth probe slice would close this gap if needed; not in scope for Phase 1.3.

*Real-keys validation.* With real keys and the dev server running, `/api/ask` produced a `publius-ask` trace in the Langfuse UI with `retrieval` (0.72s) and `generation` (1.93s, 1920→31 tokens) children, `source=route`, `prompt_sha256` matching runC's pin, and `k=3`. All four spec checks land: HTTP 200, trace present in UI, retrieval hash + scores + latency captured, generation tokens + model + latency captured.

**Conclusion.** Phase 1.3 observability is wired and validated. Both the route and the harness emit traces through a single audit point. The error-mode discipline is verified — bogus keys do not break the route, transport failures log with an `[observability]` prefix, and the bad-credentials silence is documented as a known limitation. **Path from prompt v0.1 to applied corpus:**

*v0.1 prompt and the silent-substitution problem.* The first version of the system prompt instructed the model to render Federalist paragraphs into modern American English while preserving every argument, distinction, and connective, with an `[AMBIGUOUS: ...]` flag for genuinely ambiguous passages. Gate-1 sampling against ten hand-picked paragraphs surfaced a category of failure the AMBIGUOUS-only flag could not catch: 18th-century vocabulary whose semantic field has shifted enough that a silent modern substitution loses the original meaning, and conspicuously rhetorical phrasings whose argumentative work would be smoothed away by neutral modernization. Both classes of substitution were correct in surface form (the model did not hallucinate or distort), but the editorial trace was being silently discarded — there was no review channel for "I substituted this word; here is what the original carried that the modern equivalent doesn't."

*v0.2 rewrite — three-flag system.* v0.2 keeps the v0.1 discipline (preserve argument structure, preserve logical connectives, preserve every distinction, do not editorialize, output the rendered paragraph only) and adds two new flag categories: `[WORD: "original word" — note on the semantic shift and what meaning is at risk of being lost]` for terms whose 18th-century semantic field differs from the modern default, and `[RHETORIC: "original phrase" — note on the rhetorical work it is doing]` for passages where the language is conspicuously pointed, ironic, or crafted beyond what plain statement requires. The three-flag system gives the model a structured channel to surface editorial concerns rather than silently absorbing them. The postprocess regex in the script splits all three flag types into a sidecar flags channel so the rendered paragraph stays clean while the editorial trace is preserved per-paragraph.

*Two-gate workflow with separated fetch and apply.* Gate-1 is a 10-paragraph sample chosen across the coverage matrix (Hamilton/Madison/Jay × undisputed/disputed/joint × with and without footnote markers, including a paragraph from the disputed twelve and one from the joint Federalist 18). Sample paragraphs are resolved by substring matching on a unique opening phrase, not by paragraph index, so the sample stays stable if indices ever shift. Gate-2 is the full 1,219-paragraph run (every English-source paragraph except salutations). The full run writes results to `.batch-results.json` (a sidecar keyed by `custom_id`) but does not mutate the corpus; corpus write requires a separate `--apply` invocation, which reads the sidecar, validates length-alignment per paper, and atomically rewrites `federalist.json`. The two-step pattern means even an accidental re-run of the full mode cannot overwrite the corpus without explicit operator action.

*Salutations and footnote markers.* The salutation `"To the People of the State of New York:"` is bypassed at request-build time (never submitted) and written through verbatim at apply time. Footnote markers like `(1)` / `(EN)` / `(TN-X)` are required to round-trip — the postprocess pass compares marker multisets between original and rendering, and emits a warning if any marker is dropped, gained, or duplicated. No such warnings fired across the 1,219 paragraphs.

*Direct-invocation guard.* During gate-1 work, an `await import("./scripts/generate-plain-english.ts")` smoke test triggered the script's top-level `main()` and submitted an unauthorized full-mode batch of 1,219 requests. The batch was cancelled within ~30 seconds with zero successes, but the incident motivated a structural fix: the script's `main()` invocation is now gated behind an `import.meta.url` direct-invocation check, so importing the module does not run the side-effecting entry point. The guard is documented as the canonical reference pattern for any future scripts in the project that auto-execute a `main()`.

*Fed 57 ¶16 transcription error.* During post-batch sidecar inspection, an `[AMBIGUOUS]` flag on Federalist 57 ¶16 surfaced an oddity in the source text: `"the intrigues of the ambitious or the ambitious or the bribes of the rich"` — a duplicated phrase. The model's rendering elided the duplication and noted in the flag that the source appeared garbled. Inspection confirmed the duplication was present in the corpus (`data/federalist/federalist.json`) and in Yale Avalon's transcription. Founders Online — the scholarly edition prepared from the Papers of James Madison — gives the passage without the duplication: `"the intrigues of the ambitious, or the bribes of the rich."` The duplication is therefore a transcription artifact introduced downstream of the printed source, not an authorial feature. The corpus was corrected to match Founders Online; the original and corrected text are recorded both in `paper.corrections[]` (machine-readable) and `data/federalist/CORRECTIONS.md` (human-readable). The `--retry federalist-57-para-16` path was added to the script for this correction and re-renders the single paragraph synchronously against the v0.2 prompt and atomically replaces its sidecar entry. The new rendering carries no flags — the AMBIGUOUS condition that originally surfaced the issue was resolved by fixing the source.

*Flag density across the applied corpus.* The full v0.2 batch produced approximately 1,188 `WORD` flags, 327 `RHETORIC` flags, and 16 `AMBIGUOUS` flags across the 1,219 paragraphs (post-retry the AMBIGUOUS count in the applied corpus is 15, because the Fed 57 ¶16 re-render eliminated its flag). Many paragraphs carry multiple flags of the same kind (e.g., a single paragraph may have several `WORD` flags for distinct semantic-shift cases); some carry none. The flag stream is the input to Phase 3.2 editorial review.

*Editorial decisions made during review.* Two non-trivial editorial calls were made during sidecar inspection, both worth carrying forward. (1) **Federalist 43 ¶18, Madison's slavery euphemism.** Madison's reference to "an unhappy species of population... who, during the calm of regular government, are sunk below the level of men; but who, in the tempestuous scenes of civil violence, may emerge into the human character" was flagged `[AMBIGUOUS]` by the model, with the flag note posing two readings: (a) the studied indirection is deliberate authorial evasion (a conspicuous avoidance of naming slavery while invoking its military significance), or (b) the vagueness is rhetorical caution rather than evasion, leaving open which population is meant. The owner resolved this as (a) — deliberate authorial evasion, not genuine textual uncertainty. The interpretive framing belongs in editorial commentary, not in the rendering itself; the model's instinct to flag rather than commit was correct, and the resolution belongs to the editorial layer that consumes the flag stream. (2) **Federalist 57 ¶16, "wealthy" and "scheming."** The post-retry rendering substitutes "wealthy" for "the rich" and "scheming" for "intrigues." Both substitutions are accurate modernization of what the founders meant: in the 18th-century semantic field, "the rich" denoted entrenched propertied power, not the modern reader's default of new money or celebrity wealth, and "wealthy" carries the structural-class meaning more reliably than "rich" does in 2026 English; "scheming" carries sufficient specificity for "intrigues." These are recorded as accepted renderings, not as editorial concerns.

Atomic write via temp-file + rename. Sidecar and state files cleared on success. Flags are emitted to the apply-step warning channel but are not stored in the corpus (per design at this phase); the per-paragraph flag stream is therefore consumed at apply time and not preserved in `federalist.json`. Phase 3.2 will need to either re-run the batch and capture flags before apply or extend the corpus schema with a `flags[]` field.

**Path from "no flag storage" to populated annotations file:**

*Decision: external file, not a corpus extension.* Phase 3.1 left the choice open between (a) extending the corpus schema with a `flags[]` field (and re-running apply) or (b) writing flags to an external annotations file. Option (b) was chosen for three concrete reasons. First, `federalist.json` is the source of truth for retrieval — it feeds the embedding index and is bundled into Vercel deploys; editorial churn on per-paragraph `editorial_status` and `editorial_note` should not invalidate the index or balloon the deploy bundle. Second, the cross-corpus base schema in `data/SCHEMA.md` is universal-base + namespaced extensions (`federalist: { ... }`, `tocqueville: { ... }`); flags-and-editorial-state is not corpus-specific in shape but is annotation-specific in lifecycle, and adding it as an extension confuses two different cadences. Third, an external file lets a single-paragraph re-render (the `--retry` path) update annotations without rewriting the entire corpus JSON. The schema is therefore corpus-tagged at the top level (`corpus: 'federalist'`) and will recur as `data/tocqueville/tocqueville-annotations.json` and `data/court/court-annotations.json` when those corpora reach the same phase, keeping a single shape across all three.

*Schema decisions reasoned through.* The annotations file is **dense, not sparse** — every paragraph has an entry whether it carries flags or not, because per-paragraph editorial state needs a slot regardless of flag count and because dense alignment makes the file directly indexable by `(paper_number, paragraph_index)` without lookup gaps. Salutations are present with `bypassed: true` rather than omitted, so a reviewer reading the file sees the salutation discipline explicitly rather than inferring it from absence. `term` is parsed out of the v0.2 flag body and stored separately from `note` because the prompt's flag form (`"term" — note`) is consistent for WORD and RHETORIC but AMBIGUOUS often has no term — making `term` nullable and pre-parsing both lets editorial UI render the term prominently without re-parsing on every read. The `prompt_sha256` field is pinned at apply time and embedded in the file: when editorial review consumes annotations months later, the hash answers "were these flags generated against the prompt I'm reading right now?" without any version-string ambiguity. (Pinning the hash was a small late addition during the walk-through, not part of the original sketch.)

*Abort-by-default vs merge.* The first apply writes annotations clean. Subsequent applies refuse to overwrite — by design — because a naive overwrite would erase any `editorial_status` and `editorial_note` values added during review. Re-running flag generation against an already-reviewed corpus requires explicit operator action: either delete the file (discarding editorial state, full clean rewrite) or pass `--apply --merge-annotations` (preserves editorial state per `(paper_number, paragraph_index)`, replaces flag content). The merge logic walks the existing file once into a `Map`, then constructs the new annotations from the current sidecar with prior editorial fields copied in where keys match. *Editor flow design.* `mkdtempSync(tmpdir() + '/publius-review-')` per edit, write the current `plain_english[paragraphIndex]` to `paragraph.txt`, `spawnSync(editor, [path], { stdio: 'inherit' })` so vi/nano/emacs takes over the tty, on exit read the file back. The temp directory is cleaned up in a `finally` so a thrown error in the middle of the flow doesn't leave temp artifacts behind.

*Atomic-write discipline mirrors `generate-plain-english.ts`.* `atomicWriteJson(path, obj)` writes `JSON.stringify(obj, null, 2) + '\n'` to `path + '.tmp'` and renames over the target. Trailing newline matches the existing files (the generate script writes the same way), so a successful review session produces no spurious whitespace diff against the prior file. Annotations is rewritten on every `a`/`e`/`f`/`m`/`u` action; `federalist.json` is rewritten only on `e` and only when the text actually changed. The annotations file is ~860 KB and writes in well under 10 ms — per-keystroke flush is cheap enough that the spec's "no explicit save" semantics work without buffering or debouncing.

*In-memory hold + flat flagged index.* Both files are read once at startup into JS objects and never re-read. The flat `FlaggedRef[]` index caches `(paperNumber, paragraphIndex, itemIdx, paperAnnIdx, paraAnnIdx)` per flagged paragraph in document order — the indices into `corpus.items` and `ann.papers[].paragraphs[]` are precomputed so a mutation lands without a per-keystroke scan. The cursor is just an integer into this list; `n`/`p` increment/decrement it, `g` does a `findIndex` over the list. The pre-bypassed salutations have `flags: []` and so are naturally excluded from the index — no special-casing the bypass at navigation time.

*Cursor-on-action choices.* `a`/`e`/`f` advance on success because the dominant editorial flow is "decide on this paragraph, move to the next." `m` (set note) and `u` (unset) stay because they are corrections to the current paragraph, not commitments — advancing would force a `p` immediately to undo the navigation. `g` lands wherever the user named, with the error-on-unflagged contract: the tool's surface is the flagged stream, and silent landing on a non-flagged paragraph would let the user lose track of which paragraphs are in scope. Edge cases at the start and end of the stream print `(start of flagged stream)` / `(end of flagged stream)` and stay rather than wrapping; a wrap would be a stronger UX claim than the slice warrants.

*Direct-invocation guard.* Same pattern as `generate-plain-english.ts`: `resolve(process.argv[1]) === fileURLToPath(import.meta.url)` gates `main()` so an `await import(...)` smoke test cannot kick off an interactive readline session against the live annotations file. This is the same discipline that `generate-plain-english.ts` adopted after the prior smoke-test incident, applied prophylactically here even though no review-time smoke-test pattern exists yet.

*tsc clean before showing the user.* `npx tsc --noEmit` over the project completed silently before the script was reported as ready. The script lives under the existing project `tsconfig.json` (no script-specific config); strict mode + `allowImportingTsExtensions` cover the `.ts`-extension import from `data/eval/lib.ts`.

### The cross-corpus schema is universal-base + typed extensions

Every item across every corpus shares a base schema (id, corpus, item type, authors, dates, text, paragraphs, footnotes). Each corpus then adds a single namespaced extension object — `federalist: { ... }`, `tocqueville: { ... }`, eventually `court: { ... }` — for fields specific to that corpus. New corpora must conform, not introduce one-off structures. `data/SCHEMA.md` is the authority.

`plain_english` (a Phase 4 register-modernization field for English-source corpora, generated via Claude Batch API) and `translation` (a Phase 4 cross-language field for Tocqueville, owner-authored) are intentionally separate fields with different workflows. These were originally a single field and were split during Phase 0 implementation — do not propose merging them. The `translation` field on Tocqueville items currently sits as `null` placeholder across all 124 items; populating it is the editorial gate before Tocqueville enters the index.

### Chunking is paragraph-level body + one chunk per footnote, with header context embedded in the chunk text

A retrieval chunk is not a bare paragraph. It is the paragraph (or footnote) prefixed with a header — paper number, title, authors — separated by a blank line:

```
Federalist No. 78 — The Judiciary Department
Author: Hamilton

To the People of the State of New York: WE PROCEED now to an examination of the judiciary department...
```

This is a deliberate trade. It costs a few tokens per chunk but lets the embedding space encode authorship and paper context, which the probe set verified does not break ranking. If chunk format changes, the probe set must be re-run and re-signed before the new format is treated as accepted.

Footnotes are chunked separately, not glued onto their host paragraph. The probe set includes specific footnote-targeting probes (P05/P06/P07) to verify body-vs-footnote discrimination at retrieval time.

### The retrieval stack uses zero npm dependencies

The Phase 1.1 retrieval path uses Node 22.5+ built-in `node:sqlite` and the `sqlite-vec` extension binary loaded at runtime from `data/eval/vendor/`. The vendor directory is gitignored — every contributor fetches their own platform-appropriate binary per `data/eval/README.md`. This is the deliberate baseline for local retrieval and should be preserved unless there is a concrete reason to introduce a vector-store dependency.

The two non-obvious binding rules learned the hard way:
- `node:sqlite` does not bind raw `ArrayBuffer`. Wrap embedding bytes as `Uint8Array` over the `Float32Array` buffer.
- `sqlite-vec`'s `vec0` virtual table demands `SQLITE_INTEGER` for primary-key bindings. Pass `BigInt(rowid)` to inserts on `chunks_vec`.

Both are in the code; mention here only so an advisor reading the source isn't surprised by them.

### The probe set is a regression artifact, not a one-time test

`data/eval/probes.json` and `data/eval/results-phase1-1.md` together form the regression bar. The probe set must be re-run and re-signed if any of the following change: the corpus content (a regenerate of `federalist.json` or `tocqueville.json`), the chunk format in `data/eval/lib.ts`, or the embedding model. Adding a probe to the active set is preferred over loosening the existing pass bar. The probes were designed against actual content (specific footnote markers, specific authorship-edge cases, a deliberate negative-space probe), not against vague topical similarity.

### Retrieval results carry the metadata the Q&A layer needs to preserve epistemic distinctions

`queryIndex()` in `data/eval/query.ts` returns `Hit` objects with full metadata: `corpus`, `kind` (body / footnote), `item_id`, `paragraph_index` or `marker`, `paper_number`, `title`, `authors`, `authorship_status`, `date`, plus the chunk text and similarity score. This is deliberate. The argument/observation/holding distinction non-negotiated in `CLAUDE.md` is impossible to preserve at the Q&A layer if retrieval flattens the metadata. Don't propose a Phase 1.2 Q&A interface that strips this metadata before passing context to the model.

### Phase 2.3 Ask UI — `/api/ask` streamed as NDJSON; loading phrases rotate with a fade (2026-05-13)

The streaming TODO parked earlier today was implemented in one atomic change: `/api/ask` was switched from a single buffered JSON response to an NDJSON stream, and the Ask page replaced its "Thinking…" placeholder with a rotating bank of Federalist-cadenced loading phrases that fade between cycles. Streaming and the rotating affordance ship together because either alone misrepresents what the system is doing — a static "Thinking…" while a stream is mid-flight reads as broken, and a rotating phrase without a stream behind it is theatre.

**Locked artifacts:**

- `app/api/ask/route.ts` — switched from `askClaude()` (raw HTTP from `lib/ask.ts`) to `anthropic.messages.stream()` from `@anthropic-ai/sdk`. Returns a `Response` whose body is a `ReadableStream` with `Content-Type: application/x-ndjson`. Each line is a complete JSON object terminated by `\n`. Three event types: `{ type: 'delta', text }` per text-delta event from the stream; `{ type: 'done', citations, usage, promptSha256 }` after `stream.finalMessage()` resolves; `{ type: 'error', message }` if the stream throws after the HTTP response has already begun. Pre-stream errors (validation, retrieval failure, missing API key) still return the existing JSON error responses with the existing status codes.
- `app/ask/AskForm.tsx` — replaced the `await res.json()` block with a `getReader()` loop. State adds `streamingAnswer` (accumulated delta text, reset on each submit) and `currentPhrase` (the visible loading phrase); the old single `response` object is split into `answer` and `citations`. A `useEffect` keyed on `loading` runs a Fisher–Yates shuffle of `LOADING_PHRASES`, advances through the shuffled list every 3 s via `setInterval`, and reshuffles when the list is exhausted — with a guard that prevents the first phrase of a new pass from matching the last phrase of the previous one. The phrase is wrapped in `<span key={currentPhrase} className="loading-phrase">`, so changing the key remounts the span and re-triggers the CSS `animation`.
- `app/globals.css` — added `@keyframes phraseIn` (opacity 0→1) and `.loading-phrase { animation: phraseIn 300ms ease-in }`. The animation runs on mount; remount-on-key-change is what makes each new phrase fade in.
- `DECISIONS.md` — new entry "`/api/ask` response: NDJSON stream over single JSON" documenting the new shape, the rationale (perceived latency), and that the old JSON shape is gone with no fallback.

**The NDJSON contract.** One JSON object per `\n`-terminated line. The client must buffer until it sees a newline because deltas can cross chunk boundaries — `buffer.split('\n')` then `buffer = lines.pop()` is the canonical pattern. `stripMarkdown` and the paragraph split run only on the complete accumulated string at `done`, not on individual deltas; running them mid-stream would interact badly with partial markdown spans (e.g., a stray `**` waiting on its match).

**Langfuse span timing.** `withGenerationSpan` in `lib/observability.ts` is shaped around `() => Promise<AnthropicResult>` — a single function whose resolved value carries the answer, usage, and stop reason. Streaming splits that work in two: the iteration loop runs while the HTTP response is already being written, and usage/stop reason are only available from `stream.finalMessage()`. Rather than reshape `withGenerationSpan` (which the harness at `prompts/eval/run.ts` still depends on for the non-streaming path), the route now uses `startActiveObservation` directly inline. The askSpan is opened by a floating async task that resolves the `Response` synchronously after retrieval, then `await`s a `streamDone` promise before closing — so `output: accumulated` lands on the askSpan even though the HTTP response has long since flushed. The generation span is opened inside `ReadableStream.start()` and closes after `finalMessage()`. Both spans finalize asynchronously, after the client has started receiving deltas. This is expected and fine — the trace is for post-hoc inspection, not real-time read-back. The fall-through pattern from `withAskTrace` (run uninstrumented if the wrapper fails before `fn`) is preserved: a `started` flag inside the wrapper callback distinguishes pre-fn failures from in-flight failures, and pre-fn failures retry the work via `runStreamingAsk(null, ...)`.

**The loading-phrase mechanic.** Six phrases pulled from the cadence of Hamilton/Madison rhetorical moves — "The inquiry is before us.", "Let us trace this further.", "The matter deserves a candid inquiry.", "It remains to be considered…", "The inquiry naturally presents itself…", "Upon reflection, the question resolves into…". The list is short by design: a longer list dilutes the register, and three seconds per phrase × six phrases gives an 18-second cycle, comfortably longer than typical generation latency, so the rotation rarely wraps. Fisher–Yates shuffle per pass means a user who submits two questions in quick succession sees a different opening phrase each time. The "don't repeat the last phrase of the previous pass" guard is cheap insurance — it costs one swap and removes the only obviously-jarring failure mode (the same phrase appearing twice in a row across the reshuffle boundary).

**The key-based fade.** `<span key={currentPhrase} …>` is the React pattern for "force a remount when this value changes." A CSS `animation` on the element runs once on mount; without remount, changing the text inside the span would not re-trigger it. Setting the key to the phrase value itself means React unmounts the old span and mounts a new one whenever `currentPhrase` changes, which fires `phraseIn` fresh each time. The fade is 300 ms — long enough to read as deliberate, short enough not to delay legibility of the new phrase. No fade-out — the old phrase is gone the instant the new one mounts; the eye reads the new fade-in as a transition, not as a flash.

**Path.**

*Why the streaming change had to land with a UI affordance, not as a route-only change.* The Ask UI previously showed "Thinking…" while waiting for the full response. Streaming makes the first delta arrive much earlier than the current "Thinking…" copy implies — without a UI change, the experience worsens (the placeholder lingers, then is replaced by a complete answer in a flash, defeating the streaming illusion). Inverting the affordance — show a confident loading register while waiting for the first delta, then immediately switch to the streamed answer building in place — was the actual UX win. The streaming work was the enabler, not the feature.

*Why use `startActiveObservation` inline rather than extend `withAskTrace`.* `withAskTrace` is a clean wrapper for non-streaming work where the answer arrives as part of the resolved value. Extending it to support streaming would either bloat its signature (callback for output? two-phase resolution?) or fork into two near-duplicate helpers. Inlining `startActiveObservation` in the route keeps the abstraction honest — the harness still uses the simple wrapper for the simple case, and the streaming route owns its own lifecycle. Span finalization timing (asynchronous, after the response begins streaming) is noted in a comment at the top of the inlined block so a future reader doesn't reach for the same wrapper.

*Why the client splits paragraphs only at `done`, not on every delta.* `stripMarkdown` matches on `*`, `**`, `__` pairs. Mid-stream the second half of a pair may not have arrived yet, so a delta containing `**Hamilton` would render with literal asterisks until the closing `**` arrives. Splitting at `\n{2,}` also misbehaves if a delta lands mid-paragraph. Showing the raw `streamingAnswer` (paragraph-split but not markdown-stripped) during streaming is a deliberate compromise: it's not visually perfect, but it's the simplest correct rendering, and the brief mid-stream window where formatting is imperfect resolves the instant `done` arrives and the final paragraphs render.

*Why no fade-out on phrase change.* A 300 ms fade-out followed by a 300 ms fade-in is 600 ms during which the user cannot read the upcoming phrase. With only fade-in, the new phrase is legible the moment it appears and the fade plays as an arrival cue, not a transition. The fade-out adds nothing the eye misses.

**Verification.** `npx tsc --noEmit` clean. Dev-server smoke test is owner-side: submit a question, confirm (a) loading phrases rotate with a visible fade, (b) answer text begins building once the first delta arrives, (c) citations render after the stream closes, (d) `promptSha256` logs to console on completion. No harness eval was run — this is a UI/route boundary change, not a prompt or retrieval change, and the eval has nothing to say about it.

**Conclusion.** Perceived latency on `/api/ask` drops from "wait for the full generation" to "first delta arrives within a second or two." The loading affordance for the gap before the first delta now reads as deliberate (six rotating phrases in the Federalist register) rather than as a static placeholder. The NDJSON shape is the new contract for any future consumer of `/api/ask`. Span lifecycle for streaming is documented inline in `route.ts` so the asymmetry with the harness path is discoverable rather than surprising.

### Phase 2.3 Ask UI — typed block parser; `---` rendered as a section header (2026-05-13)

The system prompt emits `---` on its own line as a structural separator followed by a short section label (e.g., `THE CORE ARGUMENT`, `OBJECTIONS`). The pre-existing renderer (`splitParagraphs`) treated both lines as plain prose, so `---` rendered literally and the section label rendered as an ordinary paragraph — losing the structural signal the model was emitting. Replaced `splitParagraphs` with `parseBlocks` in `app/ask/AskForm.tsx`: it returns a discriminated union (`{ kind: 'paragraph' | 'header'; text }`) so the renderer can branch on shape rather than on string inspection. The parser walks paragraph segments, treats a segment whose trimmed value is exactly `---` as a structural cue that consumes its own slot (no rendered output) and flags the next non-empty segment as `kind: 'header'`. The renderer maps headers to `<h3 className="ask-section-header">` with a small-caps verdigris treatment in `app/globals.css` (`var(--accent)` — the project's accent variable is `--accent`, not `--color-accent`; spec corrected at apply time). Header detection runs only on the complete answer at the `done` event; the streaming-in-progress render uses an inline `stripMarkdown + split(/\n{2,}/)` so a half-arrived `---` doesn't briefly render its trailing prose as a header and then re-layout when the actual section label streams in. Touch was narrow per spec: `app/ask/AskForm.tsx` + `app/globals.css` only; no route, prompt, or dependency changes.

**Correction (same day).** Smoke testing two real responses showed the model's actual structural device is a standalone paragraph that is entirely `**bolded text**` (e.g., `**The functional case (Federalist No. 23)**`), not `---` followed by a label. The `---` device appears, but typically as a horizontal rule before a closing summary paragraph — the segment after it is long prose, not a short label. `parseBlocks` updated in `app/ask/AskForm.tsx` to detect both patterns: a segment whose pre-strip value matches `^\*\*(.+)\*\*$` and is ≤ 84 raw chars (80 + 4 for the markers) is promoted to a header directly; the `---`-promotes-next rule keeps its semantics but only fires when the following segment's stripped text is ≤ 80 chars, otherwise the segment renders as a paragraph. Verified against both probe responses: bold short labels become headers; the 481-char closing-summary paragraph that previously would have been mis-promoted now stays a paragraph.

### Phase 3.2 review CLI — seven QoL improvements (2026-05-15)

Surgical additions to `scripts/review-annotations.ts` to make the editorial review pass less error-prone and faster on long stretches of unreviewed units. No adapter behavior or file-format changes; the tocqueville annotations file is byte-identical before and after a full smoke test (F + u revert sequence).

**The seven changes.** (1) `g next` / `g n` — jumps to the first flagged unit with `editorial_status === null`; intercepted at the top of the `g` case before the adapter locator parser, since neither corpus's locator accepts a single non-numeric token. (2) Launch status block — printed once before the first unit, shows total / reviewed / unreviewed / accepted / flagged-for-rewrite plus a "First unreviewed" line using a new `describeUnit(unit): string` adapter method (federalist returns `Federalist No. N, paragraph K`; tocqueville returns `item_id ¶N` or `item_id [marker]`). (3) `s` toggle — flips `skipReviewed`; when on, `n` and `p` walk via `findNextUnreviewedFrom(flagged, adapter, cursor, +1|-1)` instead of plain ±1; mode displayed in the per-iteration header. (5) Session stats — additive-only counters incremented when a status transition occurs (`oldStatus !== newStatus`); printed in a "this session" subsection of the quit summary. Same-value re-applies (e.g., `a` on already-accepted, confirmed) do not increment, per owner's clarification. (6) `F` — fast-pass flag; calls `flagUnit(unit, state.editorial_note)` to preserve any existing note (don't destroy data the user didn't ask to change), no note prompt, advances. (9) Overwrite confirmation — `confirmOverwrite(currentStatus)` prompts `"This unit is already <status> — overwrite? (y/n) "` before any `a`/`f`/`F` mutation when `editorial_status !== null`; anything other than `y`/`yes` aborts with no write and no cursor movement. (10) ASCII progress bar — `[███░░░] reviewed/total`, fixed 40-char width, printed in the per-iteration header alongside the skip-reviewed mode indicator.

**Path.**

*Why a new adapter method (`describeUnit`) rather than parsing `renderUnit` output.* The launch summary's "First unreviewed" line needs an adapter-specific human label (paper number for federalist, item_id for tocqueville). The existing `LocatorResolve.describe` field looked tempting but is only produced inside `parseLocator`, which expects user input — using it would require reverse-constructing locator strings just to feed back through the parser. Adding a small `describeUnit` method is a 5–10 line addition per adapter, and the alternative — stringifying the first line of `renderUnit` — would have been brittle and tied display to layout.

*Why `F` preserves existing notes instead of clearing.* Two readings of "flag without prompting for an editorial note": (a) "set status to flagged, set note to null"; (b) "set status to flagged, leave note alone". The user's framing ("for fast-pass reviewing where the flag reason is self-evident") fits either. Chose (b) because pressing `F` on a unit that already had a deliberate note — perhaps from a prior `f` — silently destroying that note is a worse failure than the alternative. The note-prompt skip is the affordance; note destruction is not.

*Why `g next`/`g n` is intercepted before the adapter parser rather than added as adapter-level locator syntax.* "First unreviewed" is corpus-agnostic — it walks the same `flagged[]` stream both adapters produce — so it doesn't belong inside `parseLocator`. Putting it in the main loop also avoids two adapter changes and keeps the locator parsers focused on their actual job (parsing `<paper> <para>` and `<item_id> <para-or-marker>`).

*Why same-value re-applies don't increment session stats.* Per owner: stats are additive on transitions only. So `a` on null → accepted: increment. `a` on accepted (confirmed overwrite): no increment. `a` on flagged (confirmed overwrite): increment accepted (transition occurred). This matches the natural reading of "transition" and avoids inflating the session counter when the user just re-confirms a status to clear an inadvertent prompt.

*Why the progress bar lives in the main loop, not in `renderUnit`.* The bar needs `reviewed/total` which the main loop already computes for the existing `renderUnit(reviewed)` argument, and adding it inside each adapter would have been duplication. The mode indicator (`[skip-reviewed ON|OFF]`) similarly belongs in main since the toggle is held in main loop state. Single 40-char-wide bar plus the mode tag fits on one line.

**Verification.** `npx tsc --noEmit` clean. Smoke-tested against `--corpus tocqueville` with paced stdin (a stdin race with piped input — pre-existing behavior, not introduced by this change — required `sleep 0.5` between commands for reliable line delivery): launch summary fields correct (378 / 104 / 274 / 78 / 26 / `tocqueville:vol1.introduction ¶29`); `g next` lands on the reported first-unreviewed unit; `F` writes without a note prompt; `F` on the already-flagged `vol1.avertissement ¶0` triggers the overwrite prompt and rejects on `n` (no counter increment, no file write); `s` toggle visibly flips the header; session stats show `flagged_for_rewrite: 1` from the single accepted F. The annotations file's SHA matches its pre-test backup, confirming no leaked writes.

**Conclusion.** The CLI is now meaningfully faster for the common case ("walk to the next thing I haven't looked at and either F-confirm or accept") while harder to use destructively (the overwrite prompt catches the common slip of pressing `a`/`f` after navigation when you meant to navigate further). Help text reflects the additions; quit summary tells you what you did this session, not just the cumulative state.

### Constitution corpus built; `constitutional_section` redefined as ID reference (2026-05-18)

The Phase 6 seam flagged in `DECISIONS.md` ("Meta-product generalization: refused; two architectural seams kept open") was resolved pre-Phase-1.2. The U.S. Constitution is now a first-class `constitution:` corpus alongside Federalist and Tocqueville, and the universal `constitutional_section` field has been redefined to reference Constitution corpus IDs instead of free-text strings.

**Path.**

*Step 1 audit changed the scope.* The original migration plan said: audit existing free-text `constitutional_section` values on Federalist items and map them to Constitution IDs. Reading the Federalist JSON revealed every one of the 85 papers carries `constitutional_section: null`; the field was never populated. Tocqueville the same — all 124 items null. The free-text representation existed only in `data/SCHEMA.md` prose. So Step 4 collapsed from "audit and rewrite N values" to "define the field correctly before it is ever used." This finding shifted the work from data migration to schema and infrastructure.

*Schema design — the clause is the item.* The cross-corpus base schema requires `paragraphs`, `authors`, `date`, `title`. None of these have a self-evident mapping to constitutional text: is an "item" the whole Constitution, a single article, a section, or a clause? The clause won because it is the smallest independently citable unit. Articles and Sections are navigational containers in the locator (`art1.sec8.cl3`) but not items. This produced 153 items: 1 preamble, 84 body clauses, 68 amendment clauses. The locator carries only as much depth as is needed — `constitution:art5` for an article with no sections, `constitution:art3.sec1` for a single-clause section, `constitution:amdt14.sec1.cl4` when sub-clauses exist within a section.

*Clause-split decisions inside amendments.* The 14th Amendment's Section 1 splits into four canonical clauses (Citizenship, Privileges or Immunities, Due Process, Equal Protection) because each has a stable short name and is independently cited in case law. The 5th Amendment splits similarly (Grand Jury, Double Jeopardy, Self-Incrimination, Due Process, Takings). The 4th splits into Unreasonable Search-and-Seizure and Warrant Clauses despite being textually intertwined — courts treat them separately. The 6th was kept as a single item over my initial proposal to split: the amendment reads as continuous prose with no source-text breakpoints, and the eight rights it enumerates are scholarly distinctions, not enumerated clauses. The owner pushed back on splitting it; the unitary form held.

*Authors and dates.* `authors: ["Framers"]` for Articles I–VII; per-amendment proposing Congress thereafter (`["1st Congress"]` for amendments 1–10 and 27; `["39th Congress"]` for the 14th, etc.). `date` is ratification: `1788-06-21` (New Hampshire as ninth state) for the body, `1791-12-15` for the Bill of Rights, per-amendment ratification date thereafter. The 27th Amendment is an oddity — proposed 1789, ratified 1992; `authors: ["1st Congress"]`, `date: "1992-05-07"`.

*Source and verification.* Three National Archives transcription pages, fetched via `curl` and converted to plain text via `pandoc`. The parser at `data/constitution/parse.ts` does not text-parse the raw — instead it carries declarative data tables of clause text, locator, short names, and supersession links. Verification asserts that every clause's text (with bracketed elisions and source-level annotations stripped) appears as a substring of the corresponding raw file. This catches transcription errors at parse time without depending on fragile text-pattern recognition for clause boundaries (which the source doesn't mark anyway). 15 `superseded_by` links encoded from the structural facts the source itself flags: the Fugitive Slave Clause superseded by the 13th Amendment Section 1; the original electoral procedure superseded by the 12th; the 18th Amendment by the 21st Section 1; and so on.

*Schema redefinition with three states.* `constitutional_section` is now `string[] | null` of Constitution corpus IDs. `null` means "not yet editorially reviewed" — preserved on every Federalist and Tocqueville item, so the existing JSON files needed no rewrite. `[]` means "reviewed, no provision asserted." Non-empty means "reviewed, with cited provisions." On Constitution items the field is always `[]` — the Constitution is the referent. The null state was chosen over a binary `string[]` because it lets the editorial workflow audit which items still need cross-reference review; Federalist coverage is expected to be dense once the editorial pass runs.

*Parser non-idempotence discovered, mid-step.* Attempting a sanity re-run of `data/federalist/parse.ts` after a type annotation change wiped every `plain_english` array back to `null`. Reverted via `git checkout`. The parser doesn't read back its own output and unconditionally emits `plain_english: null`; the population happens in `scripts/generate-plain-english.ts` after the baseline parse. Same shape applies to Tocqueville's `translation` field. This is a parser-design bug — the parsers look idempotent but are not — and is now documented in `CLAUDE.md` so future sessions don't repeat the mistake. The Constitution parser does not have this property; it carries no externally-populated fields and is freely re-runnable.

**What this means for downstream work.**

- The `constitutional_section` field is type-stable and ready to be populated by an editorial pass when Phase 6 (SCOTUS ingestion) or earlier brings the cross-reference workflow online.
- The Q&A system prompt work in Phase 1.2 onward can reference constitutional provisions by stable ID. The Constitution items are indexable on the same retrieval terms as the other corpora.
- The "two architectural seams kept open" decision now tracks only one open seam: parameterized modes of authority in the Phase 1.2 system prompt. The Constitution-as-corpus seam is closed.

**Conclusion.** The corpus seam that was deferred to Phase 6 closed pre-Phase-1.2 because the migration cost was zero (no values to migrate) and the schema gain was real (Phase 1.2 onward can cite by ID). One parser-design bug surfaced and is documented; one architectural seam is closed; the schema now has explicit editorial-status semantics.

### Phase 3.2 review — flag review reworked into a confidence-tiered triage pipeline (2026-05-22)

The one-at-a-time flag review CLI (`scripts/review-annotations.ts`, Federalist + Tocqueville) is reworked into a two-stage pipeline: a non-interactive triage classifier sorts unreviewed flags into three confidence tiers (`accept` / `rewrite` / `manual`), and the existing interactive CLI gains a `--tier` filter so each tier can be cleared through the workflow appropriate to its risk. The full architectural decision and reasoning are in `DECISIONS.md` ("Confidence-tiered flag triage pipeline"); what follows is the path that produced it.

**Path.**

*Stage 1 — audit before building.* The owner asked for an audit pass before any pipeline code. The CLI was characterized factually: annotations live in two JSON files (`data/federalist/federalist-annotations.json`, `data/tocqueville/tocqueville-annotations.json`) separate from the corpus files; each flag record carries `kind` + (`term` or `french`) + `note` plus a post-decision `editorial_status` (`null | 'accepted' | 'edited' | 'flagged_for_rewrite'`) and `editorial_note`. There is no pre-decision triage / tier / confidence field. State at audit time: Federalist 55 reviewed of 880 flagged, Tocqueville Volume I 378 of 378 (complete during the same session — the in-progress diff was committed mid-audit at commit `14c60b0`).

*Stage 1 — sample audit on Tocqueville Volume I.* Thirty already-reviewed flags were pulled (stride sampling: 18 accepts across the 296-accept population, 12 rewrites across the 82-rewrite population) and classified by reading only the flag + original + translation, applying strict asymmetric-tolerance rules. Never auto-tier as CLEAR ACCEPT anything touching period vocabulary (the handoff doc's table includes `sauvages`, `nègres`, `moeurs`, `commune`, `peuplade`, etc.), racial / social-category terms, or an argumentative step. The result: 1 CLEAR ACCEPT (a `* * * * *` section break preserved verbatim), 5 CLEAR REWRITE (Constitution back-translations, Jefferson back-translation, NH constitution back-translation, state-constitution back-translation, `Hecwelder → Heckewelder` spelling), 24 NEEDS JUDGMENT. The critical safety signal — did anything I tiered CLEAR ACCEPT get rewritten by the owner — was zero (0/1 sampled). Did anything I tiered CLEAR REWRITE get accepted as-is — zero (0/5). The safety side held; the throughput side was lopsided (~6% accept-capture / ~42% rewrite-capture / ~80% manual). Stage 1 report attached to the conversation as the input to the Stage 2 plan.

*Stage 2 plan — rubric extraction from `EDITORIAL_REVIEW_HANDOFF.md`.* The handoff document (committed at `74bc860`) is the authoritative source for what an "accept" or "rewrite" looks like in each corpus. Two corpus-specific rubrics were extracted with section citations: the Federalist rubric maps WORD / RHETORIC / AMBIGUOUS flag kinds against the handoff's "Preserve these words" table (17 entries; treated as a hard guard against CLEAR ACCEPT even when the rendering looks correct — owner-confirmed, asymmetric tolerance applied consistently) and "Consistent substitutions accepted" table (8 entries; the only CLEAR ACCEPT pattern besides false-alarm flags). The Tocqueville rubric maps READING / TEXTURE / TERM flags against the period-vocabulary table (13 entries; hard NEEDS JUDGMENT guard), the established term renderings table (~35 entries; the CLEAR ACCEPT candidates when the rendering matches verbatim), the spelling standardizations table, and the "Restore English originals" list (the CLEAR REWRITE candidates — Stage 1 audit confirmed these classify reliably). Conflicts and stale items in the handoff document were surfaced explicitly rather than silently reconciled: the "75 of 901" Federalist count is stale (actual 55/880); the Tocqueville rubric encodes policies (`avènement → advent`, `commune → township`, `moeurs` italicization) that are also listed under "Pending batch fixes" — the pipeline is safe because triage skips accepted units, but the dependency is recorded in `DECISIONS.md` so it is visible rather than latent.

*Stage 2 plan — schema choice between two re-triage policies.* Re-triage on prompt-version change must be either convention-based (a `--force` flag the operator remembers to set when the rubric changes) or structural (a file-level version field that the script compares against a code constant on every run). Both options were presented. The owner chose structural — convention-based discipline across stateless sessions is the exact failure mode the project avoids elsewhere. The schema therefore adds file-level `triage_rubric_version` (human-readable string, primary value when reading the annotation file directly) and `triage_rubric_sha256` (auxiliary; detects rubric source drift within a single named version). The original three per-record nullable fields (`triage_tier`, `triage_rationale`, `triage_generated_at`) are unchanged.

*Stage 2 plan — observability verification.* The original plan said the triage script would "match the existing batch-script pattern" for observability. Per the owner's instruction to verify before silently building: `lib/observability.ts` provides Langfuse wrappers used by `app/api/ask/route.ts` and the harness, but the existing batch-generation scripts (`scripts/generate-translation.ts`, `scripts/generate-plain-english.ts`, `scripts/retry-flagged.ts`) do not import them. "Match the pattern" therefore means: no Langfuse on the triage script. Adding it would be net-new scope for batch jobs and is held as a separate decision rather than silently bundled.

*Stage 2 plan — deferred rubric-calibration loop.* The schema captures owner override telemetry by design: `triage_tier` is independent of `editorial_status`, so a record with `triage_tier: 'accept'` and `editorial_status: 'flagged_for_rewrite'` carries a usable signal — the classifier said `accept`, the owner disagreed. Nothing in this build consumes that telemetry. The per-corpus rubric is extracted once and is otherwise static. A future rubric-calibration step — reading accumulated divergences, summarizing where the classifier and the owner disagree, and presenting that to the owner for a human decision on whether the rubric needs revision — is explicitly deferred. Recorded in `DECISIONS.md` so the half-built feedback loop is documented rather than accidental. Distinct from the retry pass: the retry pass refines prose translation policy via owner-approved system-prompt synthesis; rubric calibration would refine the triage classifier's structured rules. Both human-gated; neither auto-updates editorial standards.

*Build sequence.* One commit per step per section G of the approved plan:
1. Documentation first (this entry, the `DECISIONS.md` entry, and a brief `publius_project_plan.md` cross-reference) — committed alone.
2. Schema migration script + run — adds three null per-record fields and two file-level fields to both annotation files atomically.
3. `scripts/triage-annotations.ts` — non-interactive classifier runner using Claude Sonnet 4.6 (consistent with CLAUDE.md's "Sonnet 4.6 for Q&A" stack; the existing generation scripts use Opus 4.7 but classification is the smaller-model job). Per-corpus rubric is a hard-coded constant in the script; the classifier prompt is built from it; the SHA-256 of the canonicalized rubric is written into `triage_rubric_sha256`. Atomic per-record writes so the script is resumable. Default skips records with non-null `triage_tier`; mismatch on `triage_rubric_version` triggers re-triage of the whole corpus. Error handling: one JSON-parse retry, then default to `manual` with a rationale recording the parse failure.
4. `scripts/review-annotations.ts` extension — adds `--tier=accept|rewrite|manual` filter and a one-line `triage_rationale` display above the FLAGS block when non-null. The accept-tier flow shows the full batch (locator + rationale + flags) before a single confirm prompt; on `y`, walks the batch and calls `acceptUnit` per record. The rewrite-tier and manual-tier flows reuse the existing per-unit review machinery, filtered. The existing no-flag invocation is unchanged.

**Resulting state.** The pipeline is corpus-agnostic infrastructure; both Federalist and Tocqueville participate via the same annotation-file additions and the same two CLI scripts. The retry pass workflows for both corpora are untouched — they read `editorial_status === 'flagged_for_rewrite'` and `editorial_note`, neither of which is written by the triage path. Volume II Tocqueville is not yet started; when it does, its annotations file will conform to the same schema and the same triage pipeline applies.

**Conclusion.** The throughput improvement is concentrated in the rewrite-tier diff flow and the pre-filled rationale on the manual tier; the accept-tier batch is small by design (asymmetric tolerance, no carve-out for period vocabulary). The schema is structurally safe against rubric drift across stateless sessions because the file-level version field is checked on every run. The half-built rubric-calibration feedback loop is documented as deferred, not accidental.

### Phase 3.2 review — triage rubric v2 (exhaustive tables) and Volume I back-test (2026-05-22)

A 20-flag Federalist smoke run of the v1 classifier surfaced a rubric-adherence bug: the model read the settled-substitution tables as illustrative rather than exhaustive, auto-accepting three substitutions that were not table entries. v2 tightens the rubric language to make the tables verbatim-exhaustive and validates the fix against Tocqueville Volume I as a labeled test set.

**Path.**

*The v1 smoke run.* `node --experimental-strip-types scripts/triage-annotations.ts --corpus federalist --limit 20` classified the first 20 unreviewed Federalist flags. 3 accepts, 1 rewrite, 16 manual. The rewrite (Federalist 8 ¶12) caught a genuine truncation — `felicity` dropped, leaving `"This peculiar of situation"` — that matches the rubric's CLEAR REWRITE pattern. One of the three accepts (Federalist 9 ¶9, `assemblage` preserved verbatim against a substitution-risk flag) was a clean false-alarm match. The other two were the problem: Federalist 8 ¶11 auto-accepted `proportionably → proportionally` and Federalist 9 ¶4 auto-accepted `contracted → limited` and `adverted to → considered`, with rationales describing all three as "settled substitutions" — although none appears in the 8-entry "Consistent substitutions accepted" table. The model had read the table as illustrative of an "archaic-to-modern adverbial update" pattern and was judging novel substitutions against that pattern.

*The asymmetric-tolerance read.* This is precisely the failure mode the rubric was designed to prevent. The accept tier is the one tier where a wrong call ships without human inspection. The Stage 1 audit had shown the rule worked when applied strictly; the v1 prompt did not make strictness explicit enough. "Accepts only on verbatim table membership" had been the intent; the rubric text did not say so.

*Owner consultation before any rubric edit.* Per the task discipline, the smoke-run output was presented to the owner with full renderings before any code change. Two interpretive options were on the table: (a) seal the tables and route the three substitutions to NEEDS JUDGMENT; (b) add the three substitutions as legitimate settled mappings. The owner rejected (b) on substantive grounds and on a procedural-discipline ground:

- `proportionably → proportionally`: the v1 flag itself noted register loss ("precise calibrated relationship vs. rough approximation"). A substitution the flagging pass raised a concern about is by definition not settled.
- `contracted → limited`: slightly off-axis from Montesquieu's point (Montesquieu argues for a SMALL republic, not merely a bounded one).
- `adverted to → considered`: closer to viable but still a live editorial call.

The procedural-discipline point: the Federalist table is thin because Federalist review is barely started (55 of 880 paragraphs reviewed). Adding entries reactively from triage output would let the classifier shape the editorial standard it is meant to be measured against. The standard must be owner-derived from review work in context. This established the standing principle that the triage classifier is not a source of additions to the substitution tables — recorded in `DECISIONS.md` "Triage rubric v2 — tables are EXHAUSTIVE, no reactive additions."

*v2 rubric tightening.* Both rubrics gain explicit EXHAUSTIVE markers on every settled-substitution and established-rendering table, plus an explicit instruction: a substitution qualifies for "accept" only if the flag's term is a verbatim member of the table AND the rendering uses the table's right-hand value verbatim. Similarity is not membership. Version constants bump from `federalist-v1`/`tocqueville-v1` to `federalist-v2`/`tocqueville-v2`. The structural re-triage policy (file-level `triage_rubric_version` compared against the code constant on every run) will re-classify the 20 already-tagged smoke-run records on the next run.

*Classifier QoL fixes accompanying v2.* The `parse_failures` metric is renamed `parse_retries`, and a separate `parse_terminal` counter is added for the actual "defaulted to manual" cases — the v1 metric conflated retries with terminal failures. `max_tokens` bumps from 256 to 512 as defense-in-depth against truncation-driven parse failures (smoke-run rationales averaged 178 chars, peaked at 226). Raw output on first-attempt parse failure logs to `/tmp/triage-debug-<corpus>.log` for diagnosability.

*Volume I back-test as validation gate.* Tocqueville Volume I is fully reviewed — 378 units, 296 accepted, 82 flagged_for_rewrite, all real owner decisions. It is a labeled test set. The v2 classifier is run against the already-decided units (compute and record `triage_tier` only; never modify `editorial_status`). A confusion matrix is built. The safety-critical metric is how many units the classifier tiers `accept` that the owner actually flagged_for_rewrite. That number must be at or very near zero; if not, v2 is not done.

To enable the back-test without altering owner decisions, the triage script gains an `--include-reviewed` flag: candidates include records with `editorial_status !== null`, and the apply path is unchanged (writes only `triage_tier` / `triage_rationale` / `triage_generated_at`; never modifies `editorial_status` or `editorial_note`). `--include-reviewed` is a back-test mode by design, not part of the normal pipeline.

*Volume I back-test result — Gate FAILED.* The v2 classifier ran against all 378 Volume I units. Classifier distribution: 18 accept (4.8%), 29 rewrite (7.7%), 331 manual (87.6%). Classifier mechanics improved on v1's smoke run: 22 first-attempt parse retries (5.8%), 2 terminal (0.5%) — well below v1's 25% first-attempt rate, vindicating the max_tokens 256→512 bump.

The confusion matrix:

```
classifier  → owner:     accepted    flagged_for_rewrite    edited
  accept                    17        1                       0
  rewrite                    7       22                       0
  manual                   272       59                       0
  ────────────────────────────────────────────────────────────────
  owner totals             296       82                       0       (n=378)
```

The safety-critical number is **1 of 378 — not zero**. The one case is `tocqueville:vol1.t1.notes.C ¶12`: the classifier rationale claimed "rendering shows corrected form" of the `Hecwelder → Heckewelder` spelling standardization, but the actual rendering contains `Hecwelder` (uncorrected). The rendering was misread, not misjudged. The rubric's "Spelling standardization not applied → REWRITE" pattern would have fired correctly had the classifier read the rendering accurately; instead the classifier described a rendering that was not there.

This is qualitatively different from a borderline-judgment failure. It is a hallucination about rendering content — the kind of error the exhaustive-tables fix in v2 does not address. v2's tightening fixed rule-overgeneralization; rendering-misreading needs a different mitigation.

*Divergence breakdown — all 8 cases verified case-by-case.* The owner's discipline was to check each divergence individually rather than generalize. The standard applied: does the classifier's rationale make a factual claim about the rendering's content (explicit or implicit through pattern-matching) that is actually true of the rendering?

The 7 classifier-rewrite × owner-accepted cells, audited one by one against the actual translation text:

1. `vol1.part1.ch2 ¶86` (moeurs italicization) — classifier said rendering shows non-italicized "mores"; rendering does. **TRUE claim. Real catch.**
2. `vol1.part1.ch5 ¶11` (lumières → enlightenment) — classifier said rendering uses "enlightenment"; rendering does, four times. **TRUE claim. Real catch.**
3. `vol1.part1.ch5 ¶33` (moeurs italicization) — classifier said rendering shows non-italicized "mores"; rendering does. **TRUE claim. Real catch.**
4. `vol1.part1.ch8 ¶460` (moeurs italicization) — same shape; **TRUE. Real catch.**
5. `vol1.t1.notes.N ¶4` (Constitution Art II §4 back-translation) — classifier said rendering has "or misdemeanors" diverging from canonical "and Misdemeanors"; rendering does. **TRUE claim. Real catch.**
6. `vol1.part2.ch5 ¶23` (moeurs + lumières) — classifier said rendering uses "enlightenment and above all mores"; rendering does. **TRUE claim. Real catch.**
7. `vol1.part2.ch10 ¶451` (chapter heading moeurs) — classifier cited rewrite pattern 4 ("Chapter heading with 'moeurs' left untranslated"). Pattern 4 requires the rendering to contain "moeurs" verbatim. Rendering shows "mores" — correctly translated. The pattern does not match. **Cause AMBIGUOUS — not settled as hallucination.** Four possibilities considered:

   - *(a) Classifier hallucinated the rendering content* — possible but not directly evidenced. Unlike the Hecwelder case, the rationale here does not explicitly assert what the rendering shows; it cites a pattern match.
   - *(b) Classifier read the rendering correctly but misapplied the rubric pattern* — most parsimonious. The classifier likely jumped from "the original contains moeurs and this is a chapter sommaire" to pattern 4 without verifying the precondition that the rendering also contains "moeurs" verbatim. This is a rubric-reasoning error, not an input hallucination.
   - *(c) Owner made a considered override* — `editorial_note` is null; no recorded considered override.
   - *(d) Owner mis-actioned in the CLI* — non-trivial possibility. Chapter sommaires elsewhere in Vol I were accepted similarly (Stage 1 audit samples 10–11), and the handoff doc lists "mores" without italics as a pending batch fix — so accepting this unit was consistent with the owner's broader pattern, but a slip is not ruled out. Owner is best positioned to confirm.

   *Best-supported: (b), with (d) as a non-trivial alternative the owner is best positioned to determine. Confidence: medium — the classifier's internal state is not observable, so (a) cannot be fully ruled out from the rationale alone.*

Plus the 1 accept-tier safety failure (`vol1.t1.notes.C ¶12`, Hecwelder, explicit "rendering shows corrected form" assertion when rendering shows uncorrected) — **explicit FALSE claim, independent of any owner action. The one confirmed classifier hallucination in the back-test.**

**Verified totals across the 8 divergences: 1 confirmed classifier hallucination (Hecwelder safety-side), 6 real catches the owner overrode, 1 case with ambiguous cause (ch10 ¶451 wrong-rejection — best-explained by rubric-reasoning error, alternative explanations not fully ruled out).** The 6 real catches are exactly the override telemetry the deferred rubric-calibration loop (v1 entry point f) was set up to consume — five `moeurs` italicization gaps (which the handoff document explicitly lists under "Pending batch fixes — moeurs italics pass"), one `lumières → enlightenment` policy violation, and one Constitution Art II §4 back-translation divergence the owner accepted with conscious knowledge of the divergence. The override telemetry concept holds.

v2 is not validated. The one confirmed classifier hallucination (Hecwelder accept-tier safety failure) is sufficient to fail the gate on its own — it is a rendering-misreading on the safety side of the matrix, qualitatively different from a borderline judgment call. Per the task discipline ("If the back-test surfaces a failure, STOP and report rather than patching"), the full Federalist triage is not run, and no fix is designed in this session — mitigation is a design decision belonging to a fresh planning session, not a patch under momentum. Candidate mitigation paths (recorded for that future session, not chosen or pre-approved here): a verbatim-quoting instruction requiring the classifier to quote the rendering's exact text before tiering on patterns that depend on rendering content; a regex/code pre-check for spelling-standardization patterns and similar deterministic checks, outside the classifier; or removal of the spelling→accept and chapter-heading-moeurs→rewrite pathways from the LLM rubric and migration of those checks to deterministic code. The 378 back-test triage results stay in the annotation file as the v2 measurement record and to seed comparison against any future v3.

**Out of scope for this session.** The full Federalist triage (825 unreviewed paragraphs) is deferred. The Federalist rubric is known-incomplete; running the full triage before the owner has resumed review and grown the substitution table from real work would be premature. No corpus content edits in this session. No `review --tier=accept` against the smoke-run records before v2 is validated (which it is not).

Those records were reverted to the post-migration baseline (`triage_rubric_version: null`, no per-record triage_tier) before this Step 4 commit, so the commit's data scope is limited to the Tocqueville Vol I back-test. ## What a fresh advisor needs to know to advise on Phase 1.2 onward

**The next slice is Phase 1.2 — Q&A layer.** This means wrapping `queryIndex()` with a Claude API call (Sonnet 4.6 per `DECISIONS.md`), passing the retrieved hits as structured context, asking the model the user's question, and returning an answered text with citations back to the chunks. Two things should be designed before code:

1. **The system prompt.** This is the artifact `CLAUDE.md` calls highest-stakes. It must also handle the case where retrieval returns hits the question doesn't actually need, and the case where the question is out-of-corpus (the negative-space probe P13 was designed against this scenario at the retrieval layer; the system prompt has to handle it at the answer layer). Drafting the system prompt is owner-set; testing it against 10–15 real questions is a Claude Code job per `CLAUDE.md`.

2. **The HTTP boundary.** Phase 1.2 is the natural moment to introduce Next.js.
